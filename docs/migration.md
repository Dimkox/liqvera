# Liqvera component namespace migration

This is a breaking component migration published on main, not yet packaged as a new tagged release, from 0.1.0 to 0.2.0 on top of the full v0.0.5 source baseline. Python distributions/imports/CLIs, public capture configuration prefixes, generated schema identifiers and gateway identity now use Liqvera. Rebuild the browser, gateway and all Python services together; mixed old/new schema producers are unsupported.

Use a new virtual environment and fresh output directories. Do not overlay old wheelhouses, reuse an old editable install, relabel sealed JSON, rewrite signed authorities or point an unreviewed candidate at a live ledger. The current source requires a new reviewed grant bound to its own exact commit/tree before payments could be enabled; old grants cannot authorize it.

SQL migration files and their checksums are unchanged. Existing payment/entitlement records and sealed artifacts belong to their historical version. Keep the matching published application/verifier and coherent backups to read them. Migrate live state only through a separately reviewed, bounded forward migration that preserves unknown outcomes, digest bindings and consumed authority. The October 12 deployment preserves the existing ledger and sealed artifacts without applying SQL migrations or rewriting records. No JSON state migration was performed.

The wallet-free preview now uses a new October 12 live-public Liqvera report and ZIP, generated by the deployed services and independently verified offline. The browser checks their exact pinned hashes before rendering. The earlier September preview remains unchanged in Git history and prior release assets. Current build/verifier commands produce and accept the new namespace; historical bundles use the matching v0.0.5 verifier. Published release assets and third-party license/source notices retain original bytes.

For deployment rollback, retain the stopped previous containers and coherent backups identified in the production record; old images carry known vulnerabilities. Rebuild source rollback candidates in a separate environment. Do not run down migrations, recreate live volumes or restore a database independently of its sealed artifacts.

The v0.0.2 operator retains its original Compose contract and readiness-schema check for the immutable images it installs. Use source Compose for the 0.2.0 components; rebuilding the old operator with new images is not a supported upgrade.

The two retired raw-capture SQL migrations remain byte-identical recovery references under `migrations/`; current services do not apply them.
